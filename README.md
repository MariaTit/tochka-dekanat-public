# точка.

Конкурсный прототип цифрового деканата.

Реализованы SQLite, вход по логину и паролю, серверные сессии и минимальные
кабинеты двух студентов и сотрудника учебного офиса. В кабинете студента работают
расписание своей группы, оценки и успеваемость; на главной — ближайшие занятия и блок
успеваемости из базы. В «Документах» доступны подача справок, список и подробности своих
заявок с сохранением на сервере. Обработка сотрудником и уведомления ещё не реализованы.

## Что потребуется

- Node.js версии 22.13 или новее (рекомендуется Node.js 24 LTS).
- npm, который устанавливается вместе с Node.js.

Проверить установку в терминале VS Code:

```powershell
node --version
npm.cmd --version
```

В инструкциях используется `npm.cmd`: эта команда работает в Windows PowerShell,
даже если запуск `npm.ps1` запрещён настройками системы.
В macOS и Linux используйте `npm` вместо `npm.cmd`.

## Установка зависимостей

Откройте папку проекта в VS Code и выполните в терминале из корня проекта:

```powershell
npm.cmd --prefix server ci
npm.cmd --prefix client ci
```

Эти команды нужны при первом запуске и после изменения зависимостей.
Файлы `package-lock.json` фиксируют их версии и должны храниться в Git.
Перед первым запуском выполните подготовку ниже: она создаёт локальный `.env`.

Если установка сообщает об отказе в доступе к системному кешу npm, используйте
кеш внутри проекта (он уже исключён из Git):

```powershell
npm.cmd --prefix server ci --cache .cache/npm
npm.cmd --prefix client ci --cache .cache/npm
```

## Подготовка демонстрационных аккаунтов

Из корня проекта выполните один раз:

```powershell
npm.cmd --prefix server run setup
```

Команда создаст `server/.env` со случайным секретом сессий, базу
`server/data/tochka.sqlite` и три вымышленных аккаунта:

| Логин | Роль | Пользователь |
| --- | --- | --- |
| `student1` | Студент | Алина Сергеевна Ветрова, ИС-21 |
| `student2` | Студент | Марк Ильич Озёров, ЭК-22 |
| `staff` | Сотрудник | Елена Андреевна Ладова, учебный офис |

Для каждого аккаунта генерируется отдельный случайный пароль. **Команда выводит
его в терминал только при создании аккаунта. Сохраните пароли в менеджере паролей.**
Пароли не записываются в исходный код, документацию или файлы с учётными данными.
В базе остаются только хеши scrypt с индивидуальной солью.

Повторный запуск `setup` не меняет существующие аккаунты, секрет и пароли.
Восстановить пароль из хеша нельзя; сброс паролей в этом блоке не реализован.
Если `.env` уже существует, но его секрет отсутствует или слишком короткий,
команда сообщит об этом и не перезапишет файл. `server/.env.example` показывает
названия настроек и не содержит действующих секретов.

## Подготовка демонстрационного расписания

После подготовки аккаунтов выполните из корня проекта:

```powershell
npm.cmd --prefix server run setup:schedule
```

Команда применяет миграцию `002-schedule.sql` и однократно добавляет 32 вымышленных
занятия для ИС-21 и ЭК-22 на 20–28 ноября 2026 года. Она не меняет пользователей,
их пароли, сессии или секрет. Повторный запуск не перезаписывает занятия.
Обычный запуск сервера применяет только недостающие миграции и не заполняет расписание заново.
В текущей локальной базе демонстрационное расписание уже подготовлено.

Войдите как `student1` или `student2` и откройте «Расписание». Доступны «Неделя»,
«Месяц» с выбором дня, «Список» за месяц, выбор даты и «Сегодня». Время — московское.
Чтобы увидеть все демонстрационные состояния, выберите неделю 23–29 ноября:
23 ноября изменена аудитория, занятие с 24 ноября перенесено на 25 ноября в 16:30,
27 ноября есть отменённое занятие. Перенос виден на прежней и новой датах.
22 ноября занятий нет. Нажмите карточку, чтобы открыть подробности; Escape закрывает окно.
На главной показаны до трёх текущих или следующих занятий из этой же базы, без отменённых.
После 28 ноября будущих демонстрационных занятий нет; само расписание остаётся доступным по датам.

API расписания (только для студента с действующей сессией):

- `GET /api/student/schedule?from=2026-11-20&to=2026-11-28` — диапазон не более 62 дней.
- `GET /api/student/schedule/upcoming` — ближайшие занятия с учётом текущего московского времени.
- `GET /api/student/schedule/:id` — подробности своего занятия; чужой идентификатор возвращает 404.

Группа определяется по профилю на сервере; параметры выбора чужой группы не принимаются.
Ответ содержит `hasSchedule`, чтобы отличать неопубликованное расписание от свободного периода.
Занятия хранят дату, время, дисциплину, преподавателя, аудиторию, тип, статус,
исходные сведения при изменении и пояснение. Отдельного интерфейса редактирования пока нет.

## Подготовка демонстрационных оценок

После подготовки аккаунтов выполните из корня проекта:

```powershell
npm.cmd --prefix server run setup:grades
```

Команда применяет миграцию `003-grades.sql` и однократно добавляет восемь дисциплин
и 16 результатов для существующих `student1` и `student2`. Она не меняет пользователей,
пароли, сессии и расписание. Повторная подготовка сохраняет результаты, включая
последующие изменения в базе. При обычном запуске демооценки не заполняются заново.
В текущей локальной базе они уже подготовлены. Все сведения вымышлены, это не данные университета.

Войдите как студент и откройте «Оценки». Во вкладке «Текущие результаты» показаны
вид контроля, баллы и статус. Во вкладке «Аттестация» — экзамены, зачёты и их результаты.
На компьютере отображается таблица, на телефоне — карточки. Вкладки доступны с клавиатуры
(стрелки, Home/End). Пояснения к шкалам берутся из базы и доступны в «Как читать результаты».

- Текущий контроль в демоданных: от 0 до 20 баллов **за отдельную работу**, без
  суммирования и перевода в итоговую оценку. У Алины есть опубликованный результат 0.
- Демошкала экзамена: 2 — неудовлетворительно, 3 — удовлетворительно, 4 — хорошо,
  5 — отлично. Зачёт: «Зачтено» / «Не зачтено».
- `null` означает отсутствие результата, отображается «Нет результата» и статус
  «Не опубликован» / «Не выставлен». Это не академическая задолженность.
- У Алины и Марка разные дисциплины и результаты. Есть выставленные экзамены,
  зачёты и ожидающие публикации записи. Средний балл и проценты не вычисляются.
- На главной считаются дисциплины, опубликованные работы, выставленные аттестации
  и ожидающие результаты из этого же API. При отсутствии записей блок скрыт.

API: `GET /api/student/grades` — только собственные дисциплины и результаты студента
из текущей серверной сессии; дополнительные параметры отклоняются с 400.
Анонимный запрос возвращает 401, запрос сотрудника — 403. Ответы не кешируются.
Маршрутов редактирования оценок нет для обеих ролей.

Проверьте оба аккаунта, обе вкладки, 0 и отсутствие результата; обновите страницу
после перезапуска backend — оценки и вход должны сохраниться. Серверные проверки
оценок включены в общую команду `npm.cmd --prefix server test`.

## Заявки на документы

Войдите как `student1` или `student2` и откройте «Документы». Выберите «Справка об обучении»
или «Справка о периоде обучения», при необходимости добавьте комментарий до 1000 символов
и нажмите «Отправить заявку». Успешная отправка показывается после подтверждения сервера;
новая заявка появляется первой со статусом «Подана». Комментарий после отправки очищается.

В «Моих заявках» показаны тип справки, дата подачи по московскому времени и статус.
Нажмите карточку для просмотра номера, типа, даты, статуса и комментария. Окно закрывается
кнопкой «Закрыть» или Escape. «Обновить список» повторно получает заявки с сервера.
При ошибке отправки комментарий остаётся в форме; если связь прервалась, сначала обновите
список, чтобы проверить, не сохранилась ли заявка до обрыва соединения.

Проверьте оба аккаунта: у каждого свой список, который сохраняется после обновления
страницы и повторного входа. Интерфейс адаптирован для экранов от 360 px.

При запуске сервера миграция `004-documents.sql` добавляет справочник `document_types`
и таблицу `document_requests` в существующую SQLite. Старые таблицы и записи не меняются.
Отдельная подготовка и демонстрационные заявки не нужны.

Подробные типы, поля и статусы ранее не были определены в требованиях. Для первой части
выбран минимальный вариант:

- `study_certificate` — «Справка об обучении».
- `study_period_certificate` — «Справка о периоде обучения».
- Обязательное поле подачи: `documentTypeCode` из справочника.
- Необязательное поле: `comment`, строка до 1000 символов. Пробелы по краям удаляются;
  пустая строка или отсутствие поля сохраняются как `null`. Передавать `null` вместо строки нельзя.
- `id`, `studentId`, `status` и `createdAt` назначаются сервером. Единственный статус
  этого этапа — `submitted` («Подана»). Дата возвращается в ISO 8601, UTC.

API доступен только студенту с действующей сессией:

| Метод и путь | Ответ |
| --- | --- |
| `GET /api/student/documents/types` | `{ "documentTypes": [{ "code": "…", "name": "…" }] }` |
| `POST /api/student/documents/requests` | HTTP 201, `{ "request": { … } }`, заголовок `Location` с адресом заявки |
| `GET /api/student/documents/requests` | `{ "requests": [ … ] }`, только свои заявки, новые первыми |
| `GET /api/student/documents/requests/:id` | `{ "request": { … } }`, только своя заявка |

Пример тела POST:

```json
{ "documentTypeCode": "study_certificate", "comment": "Демо: по месту требования." }
```

Заявка в ответе содержит `id`, `studentId`, `documentType: { code, name }`, `comment`,
`status`, `createdAt`. Владелец берётся из серверной сессии. Дополнительные поля тела
и параметры URL отклоняются с 400, включая попытки выбрать автора или статус.
POST требует обычный для проекта заголовок `X-Tochka-Request: 1` и JSON;
проверка Origin сохраняется. Без входа — 401, сотруднику — 403, чужая или отсутствующая
заявка — одинаковый 404. Ответы не кешируются. Изменение и удаление заявок через API отсутствуют.

Обработка сотрудником, дальнейшие статусы, файлы и уведомления — следующие этапы.
Серверные тесты входят в `npm.cmd --prefix server test` и работают на отдельных базах
в `.cache/documents-tests/`, не изменяя рабочие данные.

## Локальный запуск

Нужны два терминала. Оба должны быть открыты в корневой папке `tochka-dekanat`.

**Первый терминал — backend:**

```powershell
npm.cmd --prefix server run dev
```

Сервер запустится по адресу http://127.0.0.1:3001.
Откройте http://127.0.0.1:3001/api/health: ожидаемый ответ — `{"status":"ok"}`.
Режим `dev` автоматически перезапускает сервер при изменении его кода.

**Второй терминал — frontend:**

```powershell
npm.cmd --prefix client run dev
```

Откройте http://127.0.0.1:5173 в браузере. Появятся название «точка.», маркировка
конкурсного прототипа, состояние связи с сервером и форма входа.
Введите логин из таблицы и соответствующий сгенерированный пароль.
Студент попадёт на `/student`, сотрудник — на `/staff`.

Frontend отправляет запрос на `/api/health`. Во время разработки Vite перенаправляет
запросы `/api` на Express по адресу `http://127.0.0.1:3001`.
Дополнительная настройка CORS не требуется.

Для остановки нажмите `Ctrl+C` в каждом терминале.

## Как проверить авторизацию

1. Войдите как `student1`: должны отображаться Алина Ветрова и группа ИС-21.
2. Обновите страницу: вход должен сохраниться. Остановите и снова запустите backend
   в первом терминале, обновите страницу ещё раз: кабинет остаётся доступен.
3. В том же браузере откройте http://127.0.0.1:5173/api/staff — ожидается ошибка 403.
   Если открыть страницу `/staff`, приложение вернёт студента в его кабинет.
4. Нажмите «Выйти из аккаунта». Должна появиться форма входа, а
   http://127.0.0.1:5173/api/auth/me теперь возвращает ошибку 401.
5. Войдите как `student2`: должны отображаться Марк Озёров и группа ЭК-22.
   Выйдите и войдите как `staff`: появятся Елена Ладова и кабинет сотрудника.
6. Проверьте неверный пароль: появится сообщение «Неверный логин или пароль».

Используйте выход между аккаунтами или отдельные приватные окна браузера.
Технические проверки доступа, подмены cookie, чужих профилей, истечения сессий
и перезапуска выполняются командой:

```powershell
npm.cmd --prefix server test
```

Тесты создают отдельные базы в игнорируемых папках `.cache/auth-tests/`,
`.cache/schedule-tests/`, `.cache/grades-tests/` и `.cache/documents-tests/`,
не изменяют демонстрационную базу и не выводят пароли. Запуски сохраняются
для диагностики; автоматическое удаление не выполняется.

## Хранение и безопасность

- SQLite подключена через встроенный `node:sqlite`. Миграции находятся в
  `server/src/db/migrations/` и применяются один раз с учётом `schema_migrations`.
- Пароли: scrypt, N=131072, r=8, p=1, случайная соль 16 байт.
  Параметры выбраны по [рекомендациям OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- Сессия хранится на сервере в SQLite и действует 8 часов с момента входа.
  Обновление страницы не продлевает её срок. В браузере — только подписанный
  идентификатор в HttpOnly cookie с SameSite=Lax; localStorage не используется.
- Для сохранения входа при перезапуске нужны прежние база и `SESSION_SECRET`.
  Они исключены из Git. Не удаляйте базу и не меняйте секрет между запусками.
- Локально используется HTTP, поэтому атрибут Secure отключён. При
  `NODE_ENV=production` cookie получает Secure, а `APP_ORIGINS` должен содержать
  HTTPS-адрес приложения. При размещении за одним доверенным обратным прокси
  используется `TRUST_PROXY=1`. Публикация в этом блоке не настраивалась.
- Запросы, меняющие состояние, требуют заголовок `X-Tochka-Request: 1`;
  сервер проверяет Origin и запрещает запросы чужих сайтов. CORS не включён.
- Приватные ответы помечены `Cache-Control: no-store`. Права и принадлежность
  профиля проверяются сервером. API не возвращает пароль или его хеш.
- Вход ограничен десятью неудачными попытками за 15 минут с одного IP.
  Этот счётчик хранится в памяти процесса и обнуляется при перезапуске.

API: `GET /api/health`, `POST /api/auth/login`, `GET /api/auth/me`,
`POST /api/auth/logout`, `GET /api/student`, `GET /api/staff`,
`GET /api/users/:userId` (только собственный профиль для обеих ролей).

## Проверка сборки

Из корня проекта выполните:

```powershell
npm.cmd --prefix client run build
```

Готовая сборка интерфейса появится в `client/dist/` и не попадёт в Git.
Это проверка сборки frontend; публикация и обслуживание сборки сервером
пока не настроены. Для проверки связи с API используйте режим `dev` выше.

Сервер без автоматического перезапуска можно запустить командой:

```powershell
npm.cmd --prefix server start
```

## Если что-то не работает

- **Нет связи с сервером:** проверьте, что первый терминал работает без ошибок,
  затем нажмите «Повторить проверку» или обновите страницу.
- **Не задан SESSION_SECRET:** выполните команду `setup` выше.
- **Слишком много попыток входа:** подождите 15 минут и проверьте выбранный логин и пароль.
- **Порт 3001 или 5173 занят:** остановите ранее запущенный экземпляр приложения
  в его терминале через `Ctrl+C`, затем повторите запуск.
- **Не найдена команда Node.js или npm.cmd:** установите Node.js и заново откройте VS Code.

## Структура

```text
client/
  src/
    App.jsx           — проверка сессии и выбор кабинета
    api.js            — запросы к API и обработка ошибок
    components/       — общие компоненты
    pages/            — вход и минимальный кабинет
    main.jsx          — запуск React
    styles/           — стили интерфейса
  vite.config.js      — порт frontend и перенаправление запросов API
server/
  src/
    app.js            — настройка Express
    index.js          — запуск сервера
    config.js         — серверные настройки и загрузка локального .env
    routes/           — авторизация, health, расписание, оценки и заявки на документы
    middleware/       — авторизация, роли и защита запросов
    services/         — пользователи, расписание, оценки, заявки и демонстрационные данные
    db/               — SQLite, миграции и хранилище сессий
  scripts/            — контролируемая подготовка демонстрационных данных
  test/               — автоматическая проверка авторизации, расписания, оценок и заявок
  data/               — локальная база, исключена из Git
```

Серверы доступны только на этом компьютере. Используются цвета проекта
`#7464D9` и `#F7F8FA`. Если Inter или Manrope не установлены, браузер использует
системный шрифт; загрузка шрифтов из внешних сервисов не требуется.
