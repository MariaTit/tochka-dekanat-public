# точка.

Конкурсный прототип цифрового деканата.

Реализованы SQLite, вход по логину и паролю, серверные сессии и минимальные
кабинеты двух студентов и сотрудника учебного офиса. В кабинете студента работают
расписание своей группы, оценки и успеваемость; на главной — ближайшие занятия и блок
успеваемости из базы. В «Документах» доступны подача справок, список и подробности своих
заявок с сохранением на сервере. Сотруднику доступна страница обработки заявок:
фильтры, подробности, смена статуса и отклонение с причиной. В «Уведомлениях» работают
объявления, напоминания, изменения занятий и статусы заявок с сохранением прочтения в SQLite.
В разделе сотрудника «Расписание» доступны выбор группы из базы, добавление и редактирование
занятий, перенос, отмена и восстановление с уведомлениями соответствующей группе.
В разделе сотрудника «Успеваемость» работают выбор студента и дисциплины из SQLite,
выставление и изменение экзаменов, обычных и дифференцированных зачётов с личными уведомлениями.

В обоих кабинетах работает раздел «Сообщения»: личные переписки студента и сотрудника,
история в SQLite, непрочитанные сообщения и персональные уведомления студенту со ссылкой в переписку.

## Личная переписка

Студент открывает `/student/messages` через меню, значок сообщения в шапке или «Ещё».
Нажмите «Новая переписка», выберите сотрудника и откройте разговор. Сотрудник открывает
`/staff/messages` и выбирает получателя последовательно: факультет / институт → курс →
группа → ФИО. Все адресаты берутся из существующих аккаунтов SQLite; отсутствующие
сведения обозначаются «Не указано в профиле». Используются прежние student1, student2 и staff.

Для каждой пары студент / сотрудник существует одна переписка: повторный выбор
получателя открывает прежнюю историю. Сообщения содержат имя отправителя, его роль,
дату и время по Москве. Текст — от 1 до 4000 символов, без вложений и HTML-разметки.
История сохраняется после обновления страницы, выхода, повторного входа и перезапуска сервера.
Пока нет автоматического обновления: используйте «Обновить переписки» и «Обновить сообщения».
Индикатор в навигации обновляется при переходе между разделами, возврате в окно и ручном обновлении.

При отправке сотрудником сообщение и персональное уведомление студенту фиксируются
одновременно. Уведомление в прежнем разделе «Уведомления» содержит ссылку «К переписке».
Открытие истории отмечает прочитанными только загруженные входящие сообщения и связанные
уведомления студента. Новое сообщение, пришедшее после загрузки истории, остаётся непрочитанным.
Отдельная отметка уведомления не меняет непрочитанное в чате. Повтор открытия не создаёт
уведомления. После обрыва ответа повтор той же отправки безопасен: сервер сохраняет одну запись.

Доступ к истории, отправке и прочтению проверяется на сервере: только студент и конкретный
сотрудник этой переписки. Другие студенты и сотрудники получают 404 при подстановке ID.
Отправитель определяется по сессии; подмена имени, роли или ID отправителя не принимается.
Текст отображается обычным текстом, включая введённые HTML-теги.

API одинаков для `/api/student/messages` и `/api/staff/messages`, с проверкой соответствующей роли:

| Метод и путь относительно раздела | Действие |
| --- | --- |
| `GET /` | Свои переписки и `unreadCount` |
| `GET /recipients` | Разрешённые получатели; staff также получает факультет, курс и группу |
| `POST /` | Открыть прежнюю или создать переписку: `{ recipientId }` |
| `GET /:id` | Участники и история, без изменения прочтения |
| `POST /:id` | Отправить `{ text, clientMessageId }`, где `clientMessageId` — UUID для безопасного повтора |
| `PATCH /:id/read` | Прочтение до загруженного `{ throughMessageId }` включительно |

Миграция `010-messages.sql` добавляет только таблицы `conversations`, `messages`, индексы
и триггеры. Прежние таблицы, записи, аккаунты и уведомления не пересоздаются и не меняются.
Она применится при обычном следующем запуске сервера. Повторный `setup` или демоинициализация
для переписки не нужны. В Amvera следует сохранить прежние `/data`, `DATABASE_PATH` и
`SESSION_SECRET`; текущая разработка облако не меняла. Перед будущим обновлением сохраните резервную копию.

Проверки в оригинальном проекте от 22.11.2026: миграция 010 успешно применена на
отдельной свежей резервной копии Amvera; прежние данные, уведомления и прочтение
сохранены, повтор миграции безопасен, проверки целостности и связей успешны.
Также проверен локальный production-запуск с настройками Amvera, перепиской обеих ролей,
изоляцией доступа, уведомлениями и сохранением истории после перезапуска.
Фактическое обновление облака и вход через облачный HTTPS в этих проверках не выполнялись.

В публичной копии после переноса успешно выполнены `npm.cmd test` — **142/142 теста**
и production-сборка `npm.cmd --prefix client run build`. Проверены `git diff --check`,
изменённые и новые файлы; секретов и приватных данных не обнаружено.
История загружается целиком; обновление вручную, без вложений и WebSocket.

## Что потребуется

- Node.js версии 22.13 или новее (рекомендуется Node.js 24 LTS).
- npm, который устанавливается вместе с Node.js.

Проверить установку в терминале VS Code:

```powershell
node --version
npm.cmd --version
```

В инструкциях используется `npm.cmd`: эта команда работает в Windows PowerShell,
даже если запуск `npm.ps1` запрещён настройками системы.
В macOS и Linux используйте `npm` вместо `npm.cmd`.

## Установка зависимостей

Откройте папку проекта в VS Code и выполните в терминале из корня проекта:

```powershell
npm.cmd --prefix server ci
npm.cmd --prefix client ci
```

Эти команды нужны при первом запуске и после изменения зависимостей.
Файлы `package-lock.json` фиксируют их версии и должны храниться в Git.
В корне также есть `package.json` без зависимостей: он объединяет production-сборку,
запуск и тесты, не заменяя отдельные пакеты `client/` и `server/`.
Перед первым запуском выполните подготовку ниже: она создаёт локальный `.env`.

Если установка сообщает об отказе в доступе к системному кешу npm, используйте
кеш внутри проекта (он уже исключён из Git):

```powershell
npm.cmd --prefix server ci --cache .cache/npm
npm.cmd --prefix client ci --cache .cache/npm
```

## Подготовка демонстрационных аккаунтов

Из корня проекта выполните один раз:

```powershell
npm.cmd --prefix server run setup
```

Команда создаст `server/.env` со случайным секретом сессий, базу
`server/data/tochka.sqlite` и три вымышленных аккаунта:

| Логин | Роль | Пользователь |
| --- | --- | --- |
| `student1` | Студент | Алина Сергеевна Ветрова, ИС-21 |
| `student2` | Студент | Марк Ильич Озёров, ЭК-22 |
| `staff` | Сотрудник | Елена Андреевна Ладова, учебный офис |

Для каждого аккаунта генерируется отдельный случайный пароль. **Команда выводит
его в терминал только при создании аккаунта. Сохраните пароли в менеджере паролей.**
Пароли не записываются в исходный код, документацию или файлы с учётными данными.
В базе остаются только хеши scrypt с индивидуальной солью.

Повторный запуск `setup` не меняет существующие аккаунты, секрет и пароли.
Восстановить пароль из хеша нельзя; сброс паролей в этом блоке не реализован.
Если `.env` уже существует, но его секрет отсутствует или слишком короткий,
команда сообщит об этом и не перезапишет файл. `server/.env.example` показывает
названия настроек и не содержит действующих секретов.

## Подготовка демонстрационного расписания

После подготовки аккаунтов выполните из корня проекта:

```powershell
npm.cmd --prefix server run setup:schedule
```

Команда применяет миграцию `002-schedule.sql` и однократно добавляет 32 вымышленных
занятия для ИС-21 и ЭК-22 на 20–28 ноября 2026 года. Она не меняет пользователей,
их пароли, сессии или секрет. Повторный запуск не перезаписывает занятия.
Обычный запуск сервера применяет только недостающие миграции и не заполняет расписание заново.
В текущей локальной базе демонстрационное расписание уже подготовлено.

Войдите как `student1` или `student2` и откройте «Расписание». Доступны «Неделя»,
«Месяц» с выбором дня, «Список» за месяц, выбор даты и «Сегодня». Время — московское.
Чтобы увидеть все демонстрационные состояния, выберите неделю 23–29 ноября:
23 ноября изменена аудитория, занятие с 24 ноября перенесено на 25 ноября в 16:30,
27 ноября есть отменённое занятие. Перенос виден на прежней и новой датах.
22 ноября занятий нет. Нажмите карточку, чтобы открыть подробности; Escape закрывает окно.
На главной показаны до трёх текущих или следующих занятий из этой же базы, без отменённых.
После 28 ноября будущих демонстрационных занятий нет; само расписание остаётся доступным по датам.

API расписания (только для студента с действующей сессией):

- `GET /api/student/schedule?from=2026-11-20&to=2026-11-28` — диапазон не более 62 дней.
- `GET /api/student/schedule/upcoming` — ближайшие занятия с учётом текущего московского времени.
- `GET /api/student/schedule/:id` — подробности своего занятия; чужой идентификатор возвращает 404.

Группа определяется по профилю на сервере; параметры выбора чужой группы не принимаются.
Ответ содержит `hasSchedule`, чтобы отличать неопубликованное расписание от свободного периода.
Занятия хранят дату, время, дисциплину, преподавателя, аудиторию, тип, статус,
исходные сведения при изменении и пояснение. Сотрудник управляет занятиями в `/staff/schedule`.

## Управление расписанием сотрудником

Войдите как `staff` и откройте «Расписание» в меню кабинета. Последовательно выберите
факультет / институт, курс и учебную группу: варианты получаются из профилей студентов
в SQLite. Если факультет или курс не заполнен, доступен вариант «Не указан в профиле».
Выберите дату для просмотра недели. «Добавить занятие» открывает форму; карточка
существующего занятия — редактор с кнопками отмены или восстановления.

Обязательны дисциплина, дата, начало и окончание, аудитория, преподаватель и тип
(лекция, практика, лабораторная или семинар). Даты — 1900–2100, время — московское,
окончание позже начала в пределах одного дня. Преподаватель — вымышленное имя.
Для изменения отменённого занятия сначала восстановите его. Удаление не предусмотрено.

API доступен только роли `staff` с действующей серверной сессией:

- `GET /api/staff/schedule/groups` — существующие сочетания `department`, `course`, `group`.
- `GET /api/staff/schedule?group=ИС-21&from=2026-11-23&to=2026-11-29` — до 62 дней.
- `POST /api/staff/schedule` — `{ group, subject, date, startTime, endTime, room, teacher, type }`.
- `PUT /api/staff/schedule/:id` — все семь полей занятия, без изменения группы.
- `PATCH /api/staff/schedule/:id/status` — `{ "status": "cancelled" }` или `{ "status": "restored" }`.

Без сессии возвращается 401, студенту — 403, неизвестному ID — 404; неверные поля — 400,
повтор отмены/восстановления и изменение отменённого занятия — 409. Пустое сохранение
не создаёт уведомления. Защита Origin и `X-Tochka-Request`, запрет кеширования сохранены.
Занятия и события сохраняются вместе: сбой уведомления откатывает изменение расписания.
Используется прежняя система уведомлений с независимым прочтением каждым студентом.

`008-staff-schedule.sql` автоматически применяется при следующем запуске сервера:
обновляет только триггеры, без изменения существующих занятий и уведомлений.
Повторный setup не нужен. Демозаполнение не создаёт новые уведомления о добавлении;
занятия, добавленные сотрудником, уведомляют свою группу. В существующей модели
название группы служит общим ключом расписания и групповых уведомлений.
Студенты видят актуальные сведения при открытии/обновлении соответствующего раздела.

## Подготовка демонстрационных оценок

После подготовки аккаунтов выполните из корня проекта:

```powershell
npm.cmd --prefix server run setup:grades
```

Команда применяет миграцию `003-grades.sql` и однократно добавляет восемь дисциплин
и 16 результатов для существующих `student1` и `student2`. Она не меняет пользователей,
пароли, сессии и расписание. Повторная подготовка сохраняет результаты, включая
последующие изменения в базе. При обычном запуске демооценки не заполняются заново.
В текущей локальной базе они уже подготовлены. Все сведения вымышлены, это не данные университета.

Войдите как студент и откройте «Оценки». Во вкладке «Текущие результаты» показаны
вид контроля, баллы и статус. Во вкладке «Аттестация» — экзамены, зачёты и их результаты.
На компьютере отображается таблица, на телефоне — карточки. Вкладки доступны с клавиатуры
(стрелки, Home/End). Пояснения к шкалам берутся из базы и доступны в «Как читать результаты».

- Текущий контроль в демоданных: от 0 до 20 баллов **за отдельную работу**, без
  суммирования и перевода в итоговую оценку. У Алины есть опубликованный результат 0.
- Демошкала экзамена: 2 — неудовлетворительно, 3 — удовлетворительно, 4 — хорошо,
  5 — отлично. Зачёт: «Зачтено» / «Не зачтено».
- `null` означает отсутствие результата, отображается «Нет результата» и статус
  «Не опубликован» / «Не выставлен». Это не академическая задолженность.
- У Алины и Марка разные дисциплины и результаты. Есть выставленные экзамены,
  зачёты и ожидающие публикации записи. Средний балл и проценты не вычисляются.
- На главной считаются дисциплины, опубликованные работы, выставленные аттестации
  и ожидающие результаты из этого же API. При отсутствии записей блок скрыт.

API: `GET /api/student/grades` — только собственные дисциплины и результаты студента
из текущей серверной сессии; дополнительные параметры отклоняются с 400.
Анонимный запрос возвращает 401, запрос сотрудника — 403. Ответы не кешируются.
Студенческий API доступен только для чтения; запись разрешена отдельным API сотрудника ниже.

Проверьте оба аккаунта, обе вкладки, 0 и отсутствие результата; обновите страницу
после перезапуска backend — оценки и вход должны сохраниться. Серверные проверки
оценок включены в общую команду `npm.cmd --prefix server test`.

## Управление успеваемостью сотрудником

Войдите как `staff` и откройте «Успеваемость» (`/staff/grades`). Последовательно выберите
факультет / институт, курс, учебную группу, ФИО студента и дисциплину с учебным периодом.
Все варианты берутся из существующих профилей и связей дисциплин SQLite. Пропуски в профиле
показаны явно; при отсутствии дисциплин результаты не выдумываются.

Под выбором дисциплины видны её текущие работы и все итоговые результаты. Выберите
«Экзамен» или «Зачёт» и заполните результат:

- Экзамен: оценка 2, 3, 4 или 5.
- Обычный зачёт: «Зачтено» / «Не зачтено».
- Дифференцированный зачёт: статус и отдельная оценка. 2 соответствует «Не зачтено»,
  3–5 — «Зачтено»; форма и сервер не позволяют сохранить противоречие.

«Сохранить результат» публикует ожидающую запись, изменяет выставленную или добавляет
отсутствующий вид аттестации существующей дисциплины. Редактирование сохраняет ID записи;
дубликаты сочетания «дисциплина студента + период + вид аттестации» не создаются.
Экзамен и зачёт — разные виды; обычный и дифференцированный зачёт используют одну запись.
Повтор без изменения результата не создаёт уведомления. Параллельное сохранение устаревшей
версии возвращает 409 и требует обновления результатов.

Каждое фактическое выставление/изменение создаёт личное сообщение с дисциплиной, периодом
и результатом в существующих «Уведомлениях» студента (категория «Учебный офис»).
Оценка и сообщение сохраняются одной транзакцией: сбой сообщения откатывает оценку.
Другие студенты, включая соседей по группе, его не получают. Студенческая «Аттестация»
показывает и статус, и оценку дифференцированного зачёта. Для получения новых данных
студент открывает или обновляет раздел; push/email не используются.

API только для staff с действующей сессией:

- `GET /api/staff/grades/students` — ФИО и учебные сведения для выбора студента.
- `GET /api/staff/grades/students/:studentId` — текущие и итоговые результаты студента.
- `PUT /api/staff/grades/students/:studentId/disciplines/:disciplineId/:type` — сохранить
  аттестацию; `type`: `exam` / `credit`, `disciplineId` — ID связи `student_disciplines`.
  Тело: `result` (строка), `differentiated` (boolean), `grade` (число или null),
  `expectedRevision` (текущая revision из ответа API; null только для отсутствующей записи).

Оба студента получают 403 на staff API, без входа — 401. Дисциплина должна принадлежать
указанному студенту; неверная связь возвращает 404. Неизвестные поля и параметры запрещены.
При обрыве связи или конфликте форма сохраняет ввод и требует сверки результатов перед повтором.

Миграция `009-staff-grades.sql` автоматически применяется обычным запуском сервера:
только новые колонки аттестации и защита от новых дубликатов, без пересоздания таблиц,
повторной демоинициализации или замены базы. Прежние аккаунты, результаты, расписание,
профили, заявки, уведомления и прочтение сохраняются. Если в старой базе уже были дубликаты,
они сохраняются, а неоднозначное редактирование блокируется до отдельного уточнения данных.
В Amvera миграция подготовлена для прежнего механизма запуска; облачные действия не выполнялись.

Проверки: `npm.cmd test`, `npm.cmd --prefix client run build`. Серверные тесты используют
отдельные SQLite в `.cache/staff-grades-tests/`; браузерная проверка — копию локальной базы,
без изменения основной. Интерфейс проверен в Edge от 360 px, включая перезапуск сервера.

## Заявки на документы

Войдите как `student1` или `student2` и откройте «Документы». Выберите «Справка об обучении»
или «Справка о периоде обучения», при необходимости добавьте комментарий до 1000 символов
и нажмите «Отправить заявку». Успешная отправка показывается после подтверждения сервера;
новая заявка появляется первой со статусом «Подана». Комментарий после отправки очищается.

В «Моих заявках» показаны тип справки, дата подачи по московскому времени и статус.
Нажмите карточку для просмотра номера, типа, даты, статуса и комментария. Окно закрывается
кнопкой «Закрыть» или Escape. «Обновить список» повторно получает заявки с сервера.
При ошибке отправки комментарий остаётся в форме; если связь прервалась, сначала обновите
список, чтобы проверить, не сохранилась ли заявка до обрыва соединения.

Проверьте оба аккаунта: у каждого свой список, который сохраняется после обновления
страницы и повторного входа. Интерфейс адаптирован для экранов от 360 px.

При запуске сервера миграция `004-documents.sql` добавляет справочник `document_types`
и таблицу `document_requests` в существующую SQLite. Старые таблицы и записи не меняются.
Отдельная подготовка и демонстрационные заявки не нужны.

Подробные типы, поля и статусы ранее не были определены в требованиях. Для первой части
выбран минимальный вариант:

- `study_certificate` — «Справка об обучении».
- `study_period_certificate` — «Справка о периоде обучения».
- Обязательное поле подачи: `documentTypeCode` из справочника.
- Необязательное поле: `comment`, строка до 1000 символов. Пробелы по краям удаляются;
  пустая строка или отсутствие поля сохраняются как `null`. Передавать `null` вместо строки нельзя.
- `id`, `studentId`, начальный статус `submitted` («Подана») и `createdAt` назначаются
  сервером. Дата возвращается в ISO 8601, UTC. Дальше статус меняет только сотрудник.

API доступен только студенту с действующей сессией:

| Метод и путь | Ответ |
| --- | --- |
| `GET /api/student/documents/types` | `{ "documentTypes": [{ "code": "…", "name": "…" }] }` |
| `POST /api/student/documents/requests` | HTTP 201, `{ "request": { … } }`, заголовок `Location` с адресом заявки |
| `GET /api/student/documents/requests` | `{ "requests": [ … ] }`, только свои заявки, новые первыми |
| `GET /api/student/documents/requests/:id` | `{ "request": { … } }`, только своя заявка |

Пример тела POST:

```json
{ "documentTypeCode": "study_certificate", "comment": "Демо: по месту требования." }
```

Заявка в ответе содержит `id`, `studentId`, `documentType: { code, name }`, `comment`,
`status`, `createdAt`, `rejectionReason` (причина отклонения или `null`). Владелец берётся
из серверной сессии. Дополнительные поля тела
и параметры URL отклоняются с 400, включая попытки выбрать автора или статус.
POST требует обычный для проекта заголовок `X-Tochka-Request: 1` и JSON;
проверка Origin сохраняется. Без входа — 401, сотруднику — 403, чужая или отсутствующая
заявка — одинаковый 404. Ответы не кешируются. Студенту недоступны изменение и удаление заявок.

Файлы документов — следующий этап. Смена статуса уже создаёт личное уведомление студенту.
Серверные тесты входят в `npm.cmd --prefix server test` и работают на отдельных базах
в `.cache/documents-tests/`, не изменяя рабочие данные.

## Обработка заявок сотрудником

Доступна только пользователю с ролью `staff` и действующей серверной сессией.
Войдите как `staff`: откроется `/staff` со всеми заявками студентов, новыми первыми.
Карточки показывают номер, ФИО студента, тип справки, московские дату/время подачи и статус.
Кнопки «Все», «Подана», «В работе», «Готова», «Отклонена» фильтруют загруженный список
и показывают количество записей. «Обновить список» получает актуальные данные из API.
Собственные сведения сотрудника сохранены в раскрываемом блоке «Мой профиль».

Откройте карточку: подробности загружаются отдельным запросом и содержат сведения
о студенте и его комментарий. Для поданной заявки доступно «Взять в работу», для заявки
в работе — «Отметить готовой». Из обоих состояний можно выбрать «Отклонить заявку»,
ввести обязательную причину до 1000 символов и подтвердить отказ. Пустая причина не принимается.
Готовые и отклонённые заявки доступны только для просмотра. Сохранение выполняется через PATCH;
успех подтверждается ответом сервера, список повторно загружается из API.

При сохранении блокируются действия и закрытие окна, чтобы избежать повторной отправки.
При ошибке текст причины сохраняется. При конфликте статусов или обрыве связи сначала
нажмите «Обновить заявку» и проверьте, что сохранилось на сервере. Загрузка, ошибки с повтором,
отсутствие заявок и пустой результат фильтра показаны отдельно. Диалог поддерживает
Tab, Escape и возврат фокуса; интерфейс рассчитан на ширины от 360 px.

Для проверки в браузере:

1. Подайте несколько демонстрационных заявок из кабинетов `student1` и `student2`.
2. Войдите как `staff`, проверьте список, фильтры, ФИО, комментарии и даты в подробностях.
3. Одну заявку последовательно возьмите в работу и отметьте готовой; другую отклоните с причиной.
4. Обновите страницу и перезапустите backend: статусы и причины должны сохраниться.
5. Войдите студентом, обновите «Документы» и откройте свою отклонённую заявку — причина видна.
6. Откройте `/staff` под студентом: приложение вернёт в его кабинет, API сотрудника даст 403.
7. Проверьте экран 360 px, Tab/Enter/Escape; готовую и отклонённую заявки изменить нельзя.

API также можно использовать из программы для HTTP-запросов. Вход выполняется через
прежний `POST /api/auth/login`, затем передаётся полученная cookie.

| Метод и путь | Ответ |
| --- | --- |
| `GET /api/staff/documents/requests` | `{ "requests": [ … ] }`, все заявки, новые первыми |
| `GET /api/staff/documents/requests/:id` | `{ "request": { … } }`, подробности заявки |
| `PATCH /api/staff/documents/requests/:id/status` | `{ "request": { … } }`, заявка после сохранения статуса |

Сотрудник получает те же поля заявки и объект `student: { id, fullName, email,
studentGroup, department }`. Пароли, хеши и сессии в ответ не включаются.

Правила переходов:

- `submitted` («Подана») → `in_progress` («В работе») → `ready` («Готова»).
- Из `submitted` или `in_progress` можно перейти в `rejected` («Отклонена»).
- `ready` и `rejected` — конечные статусы. Возврат назад, повтор того же статуса
  и переход сразу из «Подана» в «Готова» запрещены (409).
- При отклонении обязателен `rejectionReason`: непустая строка до 1000 символов
  без нулевого символа. Пробелы по краям удаляются. Для других статусов поле не принимается.

Примеры тела PATCH:

```json
{ "status": "in_progress" }
```

```json
{ "status": "rejected", "rejectionReason": "Демо: выбран неподходящий вид справки." }
```

PATCH требует JSON и `X-Tochka-Request: 1`; действует прежняя проверка Origin.
Неизвестные поля и параметры URL — 400, неверная/отсутствующая заявка — 404,
без сессии — 401, студенту — 403. Все ответы закрыты от кеширования.
Проверка перехода и запись выполняются в одной транзакции SQLite. Конкурирующий
запрос, чей переход стал недопустимым, получает 409; при ошибке записи изменения откатываются.

Миграция `005-document-processing.sql` применяется при следующем запуске сервера:
она расширяет статусы и добавляет причину отказа, сохраняя существующие заявки,
их ID, комментарии и даты. Повторное применение не выполняется. Рабочая база
в рамках этого этапа вручную не изменялась; миграция проверена на отдельных базах со старыми заявками.

После обработки студент видит актуальный статус по кнопке «Обновить список» или
после обновления страницы «Документы». Подробности запрашиваются заново при открытии.
Причина отказа отображается в подробностях отклонённой заявки как у сотрудника, так и у студента.
Смена статуса создаёт уведомление. Список обновляется кнопкой или при открытии раздела;
автообновление не добавлено.

Проверки сотрудника включены в общую команду тестов. Базы создаются в
`.cache/staff-documents-tests/`; проверяются миграция без потерь, переходы и причины,
права, валидация, одновременные запросы, ошибки SQLite и настоящий перезапуск процесса.

демоинициализацию. Повтор не создаёт дубликатов и не сбрасывает прочтение.

«Отклонена» с причиной. Запись статуса и уведомления атомарна: при ошибке откатываются обе.
Добавление, изменение, перенос, отмена и восстановление занятия создают сообщение своей
группе через общие триггеры. Повторное обновление без изменения сведений не дублирует его.
Интерфейс сотрудника находится в `/staff/schedule`.

API доступен только студенту с действующей сессией:

- `GET /api/student/notifications` — свои личные сообщения, объявления своей группы и общие;
  ответ содержит `notifications` и `unreadCount`, новые записи идут первыми.
- `PATCH /api/student/notifications/:id/read` с `{}` — отметить прочитанным;
  повтор сохраняет исходную дату прочтения. Чужой или отсутствующий ID возвращает 404.

ID студента и группа берутся из серверного профиля. Неизвестные поля и параметры запрещены;
другая роль получает 403, без входа — 401. Сохраняются защита изменяющих запросов и `no-store`.
Миграция `006-notifications.sql` добавляет таблицы `notifications`, `notification_reads`
и триггеры событий без изменения прежних записей. Прочтение не хранится в localStorage.

или кнопкой «Обновить список». Push/email, редактор объявлений и планировщик напоминаний
не добавлялись. Демособытия привязаны к ноябрю 2026 года. Мобильный интерфейс проверен
в Edge на 360/768/1024/1440 px; реальные телефоны, Safari/Firefox не проверялись.

## Локальный запуск

Нужны два терминала. Оба должны быть открыты в корневой папке `tochka-dekanat`.

**Первый терминал — backend:**

```powershell
npm.cmd --prefix server run dev
```

Сервер запустится по адресу http://127.0.0.1:3001.
Откройте http://127.0.0.1:3001/api/health: ожидаемый ответ — `{"status":"ok"}`.
Режим `dev` автоматически перезапускает сервер при изменении его кода.

**Второй терминал — frontend:**

```powershell
npm.cmd --prefix client run dev
```

Откройте http://127.0.0.1:5173 в браузере. Появятся название «точка.», маркировка
конкурсного прототипа, состояние связи с сервером и форма входа.
Введите логин из таблицы и соответствующий сгенерированный пароль.
Студент попадёт на `/student`, сотрудник — на `/staff`.

Frontend отправляет запрос на `/api/health`. Во время разработки Vite перенаправляет
запросы `/api` на Express по адресу `http://127.0.0.1:3001`.
Дополнительная настройка CORS не требуется.

Для остановки нажмите `Ctrl+C` в каждом терминале.

## Хранение и безопасность

- SQLite подключена через встроенный `node:sqlite`. Миграции находятся в
  `server/src/db/migrations/` и применяются один раз с учётом `schema_migrations`.
- Пароли: scrypt, N=131072, r=8, p=1, случайная соль 16 байт.
  Параметры выбраны по [рекомендациям OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- Сессия хранится на сервере в SQLite и действует 8 часов с момента входа.
  Обновление страницы не продлевает её срок. В браузере — только подписанный
  идентификатор в HttpOnly cookie с SameSite=Lax; localStorage не используется.
- Для сохранения входа при перезапуске нужны прежние база и `SESSION_SECRET`.
  Они исключены из Git. Не удаляйте базу и не меняйте секрет между запусками.
- Локально используется HTTP, поэтому атрибут Secure отключён. При
  `NODE_ENV=production` cookie получает Secure, а `APP_ORIGINS` должен содержать
  HTTPS-адрес приложения. При размещении за одним доверенным обратным прокси
  используется `TRUST_PROXY=1`. Инструкция Amvera приведена ниже.
- Запросы, меняющие состояние, требуют заголовок `X-Tochka-Request: 1`;
  сервер проверяет Origin и запрещает запросы чужих сайтов. CORS не включён.
- Приватные ответы помечены `Cache-Control: no-store`. Права и принадлежность
  профиля проверяются сервером. API не возвращает пароль или его хеш.
- Вход ограничен десятью неудачными попытками за 15 минут с одного IP.
  Этот счётчик хранится в памяти процесса и обнуляется при перезапуске.

API: `GET /api/health`, `POST /api/auth/login`, `GET /api/auth/me`,
`POST /api/auth/logout`, `GET /api/student`, `GET /api/staff`,
`GET /api/users/:userId` (только собственный профиль для обеих ролей).

В production Express обслуживает эту сборку вместе с API. Для локальной разработки
используйте режим `dev` выше; для полной production-сборки — `npm.cmd run build` из корня.

Сервер без автоматического перезапуска можно запустить командой:

```powershell
npm.cmd --prefix server start
```

## Подготовка к Amvera Cloud

Проект подготовлен к одному приложению в регионе Moscow-1, окружение **Node.js Server**,
инструмент **npm**. Публикация из этого проекта автоматически не выполняется.

### Версия Node.js и сборка

Node.js 20 не подходит: сервер использует встроенный `node:sqlite`, отсутствующий в этой
ветке. Минимум сервера — 22.13; локальная проверка выполнена на **24.22.0**, npm **11.19.1**.
Установлены React/React DOM 19.3.1, Vite 8.3.8, плагин React 6.3.0, Express 5.3.0,
express-session 1.19.0 и express-rate-limit 8.7.5. Vite и плагин допускают Node.js
20.19+ или 22.12+, но это не отменяет требования сервера к SQLite.

В `amvera.yml` указана версия **"24"**. По [документации Node.js Server Amvera](https://docs.amvera.ru/applications/environments/nodejs-server.html)
значение версии является тегом образа `node` и может задаваться вручную, даже если
генератор предлагает 20. Версия 24 выбрана без замены SQLite и библиотек приложения.
Тег `24` получает обновления в рамках этой ветки; конкретная минорная версия в облаке
может отличаться от проверенной локально.

Amvera сначала выполняет `npm install` в корне. Корневой пакет не имеет зависимостей.
Затем `build.additionalCommands` запускает `npm run build`, который:

1. Устанавливает frontend через `npm --prefix client ci --include=dev`, включая Vite.
2. Собирает React в `client/dist/`.
3. Устанавливает backend через `npm --prefix server ci --omit=dev`.

В сборку попадают только корневой `package.json`, серверный пакет, его исходники,
миграции, скрипты подготовки и зависимости, а также `client/dist/` с сохранением путей.
Локальные `.env`, SQLite, тесты и исходники frontend не включаются в артефакты.
Секреты для сборки не нужны. Запуск — `npm start` из корня, то есть `node server/src/index.js`.

### Переменные Amvera

В разделе «Переменные» добавьте значения без внешних кавычек:

| Имя | Значение |
| --- | --- |
| `NODE_ENV` | `production` |
| `PORT` | `3001`, ровно как `run.containerPort` в `amvera.yml` |
| `DATABASE_PATH` | `/data/tochka.sqlite` (также production-значение по умолчанию) |
| `SESSION_SECRET` | Отдельный случайный секрет; добавить как **секрет**, минимум 32 байта |
| `TRUST_PROXY` | `1`, для работы за HTTPS-прокси Amvera |
| `APP_ORIGINS` | Фактический `https://`-адрес приложения после получения домена |

Секрет можно сгенерировать локально и сохранить в менеджере паролей:

```powershell
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Не записывайте результат в Git или документацию. Сохраняйте один и тот же секрет между
перезапусками и обновлениями, иначе существующие cookie сессий станут недействительными.
Локальный `server/.env` в облако не загружается.

`APP_ORIGINS` — точный origin: схема и домен, без пути и завершающего `/`. При нескольких
доменах перечислите их через запятую. Пример формата: `https://your-domain.example`;
это образец, его нужно заменить настоящим адресом. Пока публичного адреса нет, значение
не подставлено. Без корректного `APP_ORIGINS` production-сервер остановится с понятной ошибкой.
После изменения переменных перезапустите приложение, как требует
[документация Amvera](https://docs.amvera.ru/applications/configuration/variables.html).

Express слушает **0.0.0.0:3001**; HTTPS завершается на стороне Amvera. В разделе «Домены»
нужно включить публичный HTTPS-адрес. В браузере используется один домен: страницы,
ресурсы React и `/api`. Отдельный адрес backend и CORS не требуются. Прямые адреса `/login`,
`/student`, вложенные разделы студента, `/staff` и `/staff/schedule` отдают React при обновлении страницы.
Неизвестный `/api/...` остаётся JSON 404; отсутствующие файлы не подменяются React.
Cookie в production сохраняет Secure, HttpOnly и SameSite=Lax.

### Постоянное хранение и первая подготовка

`run.persistenceMount: /data` монтирует отдельное постоянное хранилище. Оно отличается
от папки проекта `/app` и от локальной `server/data/`. В `/data/tochka.sqlite` хранятся
пользователи, хеши паролей, расписание, оценки, заявки и серверные сессии. Служебные файлы
SQLite `tochka.sqlite-wal` и `tochka.sqlite-shm` создаются рядом, также в `/data`.
Это соответствует [инструкции SQLite Amvera](https://docs.amvera.ru/databases/sqlite.html).

Обычный запуск применяет недостающие миграции. Без специального разрешения демоданные
не создаются. База не пересоздаётся и не очищается. Используйте **одну реплику** приложения
с этой SQLite. Существующие `/data/tochka.sqlite`, `-wal` и `-shm` нельзя удалять,
заменять или загружать поверх них локальную базу. Локальная база автоматически не переносится.

### Однократная инициализация существующей облачной базы

После обновления кода временно добавьте в Amvera следующие переменные. Пароли придумайте
отдельно для каждого аккаунта и сохраните в менеджере паролей; введите их только в поля
секретов Amvera, без внешних кавычек, команд терминала, записи в Git или документацию.

| Переменная | Как задать |
| --- | --- |
| `DEMO_INIT_ENABLED` | Обычная переменная, строго `true` |
| `DEMO_STUDENT1_PASSWORD` | **Секрет**: пароль нового `student1`, от 12 до 256 символов |
| `DEMO_STUDENT2_PASSWORD` | **Секрет**: пароль нового `student2`, от 12 до 256 символов |
| `DEMO_STAFF_PASSWORD` | **Секрет**: пароль нового `staff`, от 12 до 256 символов |

Убедитесь, что `DATABASE_PATH=/data/tochka.sqlite` и прежние настройки HTTPS сохранены.
Существующий `SESSION_SECRET` оставьте прежним: он нужен для сохранения сессий.
Перезапустите приложение с этими переменными. Инициализация выполняется до открытия порта;
сборка её не запускает. Публичных маршрутов настройки нет.

Создаются только отсутствующие `student1` (ИС-21), `student2` (ЭК-22) и `staff`.
Существующий логин проверяется без учёта регистра: его пароль, роль, профиль и группа
не меняются, секрет для него уже не нужен. Все пароли новых аккаунтов проверяются до
добавления пользователей, сохраняются только scrypt-хеши. Пароли и хеши в лог не выводятся.
Существующие сервисы `setup:schedule` и `setup:grades` добавляют 32 занятия для двух групп
и 16 результатов (8 дисциплин). Маркеры импорта защищают от дублей и изменения ранее
заполненных данных. Новых заявок и сессий подготовка не создаёт.

Как проверить результат:

1. В логах запуска найдите `Демоинициализация завершена` и числа созданных записей.
   При пустых демоданных ожидаются `новых пользователей — 3; занятий — 32; результатов — 16`.
   Нули при повторном запуске означают, что данные уже существуют. Затем должна появиться
   обычная строка запуска сервера. Логи не содержат значений секретов.
2. По публичному HTTPS-адресу войдите по очереди под `student1`, `student2`, `staff`.
   Для новых аккаунтов используйте пароли из менеджера паролей; для существующих — прежние.
   У обоих студентов проверьте расписание на **20–28 ноября 2026 года** и обе вкладки оценок.
   После 28 ноября будущих демозанятий нет, поэтому выбирайте эти даты вручную.
3. Удалите `DEMO_INIT_ENABLED` (или задайте `false`) и три `DEMO_*_PASSWORD` из Amvera,
   затем перезапустите приложение. Сохранённые аккаунты и данные останутся в SQLite.
4. В логах появится `Демоинициализация отключена`; повторите вход и убедитесь, что данные
   и существующие заявки сохранились. `SESSION_SECRET`, `DATABASE_PATH` и HTTPS-настройки
   не удаляйте.

Если появляется `Демоинициализация не завершена`, сервер завершится с кодом 1 без
сообщения об успехе. Проверьте наличие и длину секретов для новых аккаунтов, доступность
SQLite и группы существующих студентов. Этапы пользователей, расписания и оценок имеют
отдельные транзакции: завершённые этапы сохраняются, неудачный откатывается. После
исправления повторите запуск с флагом — завершённые импорты и аккаунты будут пропущены.
Если существующий аккаунт имеет другую роль или группу, подготовка оценок не меняет его
данные и сообщает об ошибке; требуется отдельное решение, сброс не выполняется.
Если аккаунт существует, а прежний пароль неизвестен, этот механизм его не восстанавливает.

Прежняя команда `npm --prefix server run setup` в production использует тот же флаг,
секреты и подготовку всех демоданных, без вывода паролей и создания `.env`. Локальный
`setup` сохраняет прежнее поведение со случайными паролями для разработки.

Если потребуется перенести именно локальные данные, это отдельный согласованный шаг:
нужна согласованная резервная копия SQLite и загрузка в **Data**, а не в **Code**.
Не копируйте только основной файл во время активной записи в WAL. Для сохранения
существующих сессий также нужен прежний секрет. В текущей задаче перенос не выполнялся.

### Локальная проверка production

Из корня:

```powershell
npm.cmd run build
npm.cmd test
```

При недоступном системном кеше npm перед сборкой задайте
`$env:npm_config_cache = Join-Path (Get-Location) '.cache/npm'` в текущем терминале.

Для ручной проверки запуска в отдельном терминале можно использовать отдельную базу:

```powershell
$env:NODE_ENV = 'production'
$env:PORT = '3001'
$env:DATABASE_PATH = Join-Path (Get-Location) '.cache/production-local/tochka.sqlite'
$env:SESSION_SECRET = node -e "process.stdout.write(require('node:crypto').randomBytes(48).toString('base64url'))"
$env:TRUST_PROXY = '1'
$env:APP_ORIGINS = 'https://tochka.example'
npm.cmd start
```

`http://127.0.0.1:3001/api/health` и прямые адреса страниц должны открываться.
Это проверка сборки и запуска: для обычного входа с Secure cookie нужен HTTPS;
локальный HTTP не заменяет проверку реального HTTPS-прокси. Не отключайте Secure ради
публикации. Остановите сервер через Ctrl+C и закройте этот терминал, чтобы production-
переменные не влияли на последующий локальный режим разработки.

Локально проверены сборка, автоматические тесты, упаковка артефактов и production-запуск
с отдельной базой: вход трёх аккаунтов через имитацию HTTPS-прокси, права, расписание,
оценки, подача/обработка заявки и сохранение всех сессий/данных после перезапуска.
В Edge проверена загрузка настоящей сборки и формы входа без ошибок JavaScript.
По сообщению пользователя, приложение уже работает в Amvera через HTTPS. Новую
инициализацию агент проверяет локально на отдельных базах; её фактическое выполнение
в облаке и сохранность `/data` после облачной пересборки нужно проверить по инструкции выше.

## Если что-то не работает

- **Нет связи с сервером:** проверьте, что первый терминал работает без ошибок,
  затем нажмите «Повторить проверку» или обновите страницу.
- **Не задан SESSION_SECRET:** выполните команду `setup` выше.
- **Слишком много попыток входа:** подождите 15 минут и проверьте выбранный логин и пароль.
- **Порт 3001 или 5173 занят:** остановите ранее запущенный экземпляр приложения
  в его терминале через `Ctrl+C`, затем повторите запуск.
- **Не найдена команда Node.js или npm.cmd:** установите Node.js и заново откройте VS Code.
