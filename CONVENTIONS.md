
# CONVENTIONS — Правила разработки проекта «Точка»

## 1. Общие правила

- Использовать JavaScript для frontend и backend.
- Писать понятный, структурированный код.
- Не усложнять архитектуру без необходимости.
- Избегать дублирования кода.
- Соблюдать CONSTITUTION.md.
- Перед изменением существующего модуля изучать его реализацию.
- Не переписывать работающие части без необходимости.

## 2. Технологии

Frontend:
- React
- Vite
- CSS

Backend:
- Node.js
- Express

База данных:
- SQLite

Не заменять технологии без согласования.

## 3. Структура проекта

Рекомендуемая структура:

- client/ — интерфейс React.
- server/ — сервер Express.
- server/routes/ — API-маршруты.
- server/middleware/ — проверки доступа и обработка запросов.
- server/services/ — бизнес-логика.
- server/db/ — работа с SQLite.
- client/src/components/ — общие компоненты.
- client/src/pages/ — страницы приложения.
- client/src/styles/ — стили.
- docs/ — дополнительная документация.

Создавать папки по мере необходимости.
Не создавать пустые модули ради структуры.

## 4. Именование

- React-компоненты: PascalCase (StudentProfile.jsx).
- Функции и переменные: camelCase (getStudentData).
- Константы: UPPER_SNAKE_CASE (MAX_FILE_SIZE).
- CSS-классы: kebab-case (student-card).
- Названия API-маршрутов: понятные английские слова.
- Имена должны отражать назначение.

## 5. React

- Использовать функциональные компоненты.
- Повторяющиеся элементы выносить в общие компоненты.
- Не дублировать бизнес-логику на разных страницах.
- Обрабатывать загрузку, ошибки и отсутствие данных.
- Не хранить секретные данные в браузере.
- Не использовать прямые обращения к SQLite из React.

## 6. Backend

- Все пользовательские данные получать через API.
- API-маршруты группировать под /api.
- Проверять входные данные на сервере.
- Проверять авторизацию и права доступа.
- Не доверять идентификаторам, переданным клиентом.
- Возвращать понятные ошибки без раскрытия секретов.
- Использовать единые правила обработки ошибок.

## 7. База данных

- Использовать SQLite через сервер.
- Применять параметризованные SQL-запросы.
- Изменения структуры базы оформлять миграциями.
- Не удалять пользовательские данные без разрешения.
- Не пересоздавать базу при каждом запуске.
- Тестовые данные добавлять контролируемым способом.

## 8. Безопасность

- Хранить пароли с использованием стойкого алгоритма хеширования.
- Не хранить пароли в открытом виде.
- Не помещать секреты в Git.
- Использовать переменные окружения для секретов.
- Не сохранять токены сессии в localStorage.
- Предпочитать защищённые серверные сессии с HttpOnly cookie.
- Проверять права на каждый защищённый объект.
- Проверять доступ при скачивании файлов.

## 9. Интерфейс

- Соблюдать дизайн-систему «Точки».
- Использовать общие CSS-переменные для цветов и размеров.
- Не растягивать изображения с нарушением пропорций.
- Обеспечивать адаптивность от 360 px.
- Использовать понятные русскоязычные сообщения.
- Для основных действий предусматривать состояния загрузки и ошибок.
- Не создавать кнопки без работающего действия.
- Учитывать доступность интерфейса с клавиатуры.

## 10. Тестирование

После каждого изменения:
- Проверять затронутую функциональность.
- Проверять отсутствие ошибок запуска.
- Проверять сохранение данных, если функция их изменяет.
- Проверять ограничения доступа для защищённых операций.
- Не заявлять о прохождении тестов, которые не запускались.

## 11. Работа с Codex

- Выполнять задачи небольшими логическими блоками.
- Перед началом учитывать контекст проекта.
- Не создавать Git-коммиты.
- Использовать терминал для установки, запуска и проверки.
- Согласовывать потенциально опасные операции.
- По окончании сообщать изменённые файлы и результат проверки.
- Обновлять PROGRESS.md после завершения блока.

## 12. Документация

- AGENTS.md — инструкции для агента.
- CONSTITUTION.md — обязательные принципы.
- CONVENTIONS.md — технические правила.
- PROJECT_CONTEXT.md — описание и архитектура.
- PROGRESS.md — фактическое состояние разработки.

Документы не должны противоречить друг другу.
Если обнаружено противоречие, сообщить пользователю.
